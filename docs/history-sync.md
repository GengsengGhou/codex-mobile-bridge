# History and synchronization

The earlier-message button sits inside the transcript at the loaded-history boundary. It scrolls away when reading recent messages. Each click loads one bounded page (up to ten turns), preserves the visible turn's offset, and advances the cursor. A failed page retains existing messages and the cursor and exposes an explicit retry. Exhausted history shows a small end marker. There is no scroll-triggered endless history loading; the existing offline catch-up remains limited to three pages before manual continuation.

Synchronization uses one scheduled poll after the preceding poll settles. Running tasks, statuses requiring attention, pending controls, unconfirmed messages and unavailable connections use about three seconds. Idle reads step through 10, 20 and 30 seconds. Hidden documents stop scheduling and stop continuing a poll into additional reads; returning to the page, focus, network recovery and completed mutations request a fresh read. Pending approvals remain visible and keep the fast cadence even if the task itself looks idle. Latest reads retrieve only the current page, retaining loaded historical turns and their cursor.

The local server computes conditional validators from freshly read JSON for status, lists, latest/history thread pages and execution controls. Authorization runs first. Responses remain `no-store`; explicit in-memory client validators avoid unchanged response bodies without persisting conversation snapshots to a browser HTTP cache. The API cache belongs to one device/account context instance, has at most 32 entries and 4 MiB estimated UTF-16 payload, excludes individual responses over 1 MiB, returns copies to callers, and clears on mutations or authentication failures. Bodyless 304 responses reuse the matching snapshot, never parse an empty body as JSON, and retry unconditionally if invalidation happened during the read.

Static scripts, styles and fonts use content SHA-256 validators with `private, no-cache` after the relevant authentication/ownership checks. HTML and authentication JSON remain `no-store`. Every browser reuse must revalidate, so changed assets are invalidated safely after an upgrade without requiring immutable versioned URL support. The temporary gateway and device hub preserve authenticated conditional transport.

## Verification

Focused tests cover bodyless 304, snapshot copy isolation, API instance isolation, mutation invalidation, server authorization before validators, fresh changed content, static cache policy, history failure/retry and exhausted cursor preservation. Browser screenshots and measurements are in `work/codex-probe/history-sync-evidence.json` and `history-{320,390}-*.png`.

The GET-only browser fixture runs the actual app/server/renderer with synthetic history. On 320 and 390 px screens, the button is offscreen at the bottom, both older pages load manually, failure is retryable, and the prepend anchor shifts by less than 1 px. It sends no chat messages. Traffic sampling accelerates both scheduling and the elapsed-time clock by 20x: an idle sample of approximately 60 seconds records 17 requests and 153 JSON body bytes (14 empty 304s), versus 52 requests and 308,768 JSON body bytes from replaying the former fixed three-second schedule against the same fixture. Counts include status, lists, controls and sidebar order. Pending interaction sampling retains the fast cadence (20 requests over about 20 seconds); a hidden 14-second interval starts zero requests. These are deterministic fixture measurements, excluding headers, TLS and WebSocket overhead, not a claim about all real conversation sizes or mobile networks.
